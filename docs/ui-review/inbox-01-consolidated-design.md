# AI 收件箱 / 待确认消息统一设计方案

## 1. 目标与范围

本轮将“AI 收件箱”收敛为与“今日工作台”一致的 **证据优先待确认消息台**。页面用于法务核对授权消息、理解上下文边界、审阅 AI 研判、人工修改正式字段，并在满足门禁时确认创建 `LegalMatter` 与首个 `WorkItem`。

本轮只调整当前前端页面、交互状态、响应式和自动化验收，不新增 UI 框架，不修改后端状态机、审核或发送门禁。任何未经当前后端路由实现的忽略、暂缓、关联、更新、补充材料或合并操作均不得伪装成功。

## 2. 独立分析结论与裁决

`product_ui_designer` 与 `ux_information_architect` 独立读取真实前后端后共同确认：

1. 当前页面以多张完全展开的 AI 研判卡为中心，缺少真正的消息队列；圆形置信度、连续彩色 Tag 和多层分析框形成典型 AI Dashboard，而不是法务审阅台。
2. `MessageAnalysis` 已提供当前消息正文、发送人 ID、时间、消息类型及 `ContextSnapshot` 摘要，但页面只显示消息 ID，法务无法以原文核对 AI 建议。
3. 所有 Candidate 都显示“确认并创建事项”；对于 `link_matter`、`update_matter`、`information_only` 或 `ignore` 建议，这会诱导重复创建正式事项。
4. 单条分析加载失败被静默吞掉，并回退显示为已完成；证据不可用时确认仍可点击。
5. 重新分析 queued/running 期间仍可能确认旧结果；前端必须冻结正式确认。
6. 当前确认 Modal 不保留证据上下文，系统占位值可能被保存为“法务已确认”；期限候选也没有明确接受或修改入口。
7. 390px 仍使用双列卡片、横向动作栏和 760px Modal，关键内容和操作没有可靠移动流程。

两份分析对“完整处置路径”方向一致，但当前正式设计文档与实际路由存在实现差距。实际代码目前只提供：

- 读取待确认 Candidate；
- 读取消息分析；
- 重新分析；
- `confirm-create` 创建 Matter 与首个 WorkItem。

因此本轮裁决为：

- 只有 `recommendedAction === create_matter`、原始消息/分析成功加载、Candidate 仍为待确认、且 AgentRun 不处于 queued/running/preparing/validating 时，才允许进入确认创建流程。
- 忽略、暂缓、关联/更新、补充材料、仅作信息和合并以禁用动作呈现，并明确“后端流程未接入，不会执行”。
- 不在前端模拟正式状态迁移，不把本地 UI 选择包装成处理成功。
- 不把历史分支或正式 API 文档中尚未落地的接口当作当前可用能力。

## 3. 唯一信息架构

页面顺序固定为：

```text
待确认消息队列
→ 原始消息
→ 上下文与证据覆盖范围
→ AI 提取结果
→ 不确定项与缺失材料
→ 人工处置与正式字段编辑
→ 影响预览
→ 确认创建
```

AI 建议必须排在原始证据之后。消息来源、AI 建议、人工输入和确定性系统状态使用稳定且不同的视觉语义。

### 3.1 页面上下文

- 标题统一为“待确认消息”，避免把“AI”作为页面主身份。
- 副标题说明“先核对原始消息和证据范围，再决定是否创建正式事项”。
- 右侧仅保留刷新；刷新不显示静态“同步成功”。
- 页面不展示未经状态接口证明的在线、已连接或同步正常。

### 3.2 消息队列

左侧为紧凑 Candidate 队列，每条只展示：

- AI 建议标题，并明确前缀“建议”；
- 消息时间和发送人 ID；
- 中文化建议动作；
- 缺失信息数量；
- 待人工确认或当前分析状态。

点击条目只切换当前详情，不修改业务状态。队列不提供没有真实数据支持的筛选器或统计。

### 3.3 原始消息

详情首区展示只读原始消息：

- 发送人 ID；
- 发送时间；
- 消息类型；
- 从结构化 `message.content` 中安全提取的正文；
- 无可读正文时明确显示“当前接口未返回可读正文”，并保留结构化内容的受控查看入口。

当前接口没有群聊名称和人员显示名时，直接标注“当前接口未提供”，不得编造。

### 3.4 上下文和证据覆盖范围

使用中性信息区展示：

- ContextSnapshot 版本；
- 纳入的消息数量和消息 ID；
- 参与人 ID 数量；
- 附件 ID 数量；
- 是否发生截断；
- 快照时间。

附件只展示真实 ID/数量与能力边界。存在附件 ID 时标注“当前仅验证元数据，未证明附件正文已解析”；没有附件但 AI 指出材料缺口时显示明确的“缺少附件/材料”提示。

### 3.5 AI 提取结果

AI 区使用低饱和辅助表面，展示：

- 建议标题、分类、动作和置信度文本；
- 研判理由；
- “消息中明确陈述（待法务确认）”；
- “AI 推断”；
- 期限候选；
- 缺失信息。

移除圆形置信度仪表盘；置信度不能替代证据。技术枚举全部中文化，AgentRun、Candidate ID、版本和哈希放入默认折叠的“审计信息”。

### 3.6 不确定项与缺失材料

- 推断、低置信度、上下文截断、附件仅元数据、分析加载失败分别有清楚状态。
- 分析详情失败时显示局部错误和重试，不回退为“completed”。
- 证据或分析不可用时禁用确认创建，并显示阻断原因。
- 重新分析进入 queued/running/preparing/validating 后冻结正式确认，旧结果只作为待替换结果查看。

### 3.7 人工处置

当前详情底部为人工决定区：

- 可用主操作：仅在安全门禁通过时显示“审阅并创建事项”。
- 可用次操作：重新分析；AgentRun 详情安全导航。
- 禁用动作：关联/更新、补充材料、仅作信息、忽略、暂缓、合并；每项标注“待后端流程接入”。

当 Candidate 推荐动作不是 `create_matter` 时，不显示可用的创建主操作，改为明确警告：“当前建议处置尚未接入，已阻止错误新建事项”。

### 3.8 人工编辑与影响预览

确认流程使用 Ant Design `Drawer`，不是脱离证据的孤立大 Modal：

- 顶部持续显示原始消息摘要、Candidate 版本和 AI 建议来源。
- AI 预填只用于建议标题、分类和背景，并标记“AI 建议，可人工修改”。
- 负责人、风险、业务影响、优先级、下一步不得用静态占位值冒充人工确认，必须由用户明确填写或选择。
- 增加首个 WorkItem 的计划完成时间字段，映射到现有 `plannedCompleteAt`；不声称已创建独立 Deadline。
- 提交前固定展示影响预览：将原子创建 1 个 Matter 和 1 个 WorkItem，记录人工确认；不会发送消息、不会绕过后续审核。
- 浏览器验收只修改表单并取消，不调用真实确认接口；正式创建仍使用既有认证、幂等和版本门禁。

## 4. 异步与边界状态

必须提供：

1. 列表加载：Skeleton，不显示假数据。
2. 空状态：明确“暂无待确认消息”，不等同于“所有分析均成功”。
3. 列表错误：Alert + 重试。
4. 401/403：独立无权限提示，不静默初始化为成功。
5. 详情加载：保留队列，详情使用 Skeleton。
6. 详情错误：显示失败原因、重试与禁用确认。
7. 分析中：显示真实状态，冻结正式确认。
8. 缺少附件：显示材料缺口及当前附件覆盖范围。
9. 版本冲突或已处理：关闭编辑态，要求刷新当前 Candidate。

本轮不新增聚合失败消息接口，因此不能声称 Inbox 已覆盖“没有 Candidate 的 failed/dead-letter 消息”；页面文案需保留该验证缺口。

## 5. 三档响应式结构

### 1440 × 900

- 228px 应用侧栏，页面 24px gutter。
- 工作区采用约 `300px 队列 + minmax(0, 1fr) 详情`。
- 详情是一个主表面，内部可使用“证据主区 + AI 辅区”，人工决定栏保持可见。
- 不使用多张完全展开 Candidate Card。

### 1024 × 768

- 应用侧栏折叠为 72px，页面 18px gutter。
- 约 `250px 队列 + 1fr 详情`。
- 详情内部单列，顺序为原文 → 范围 → AI → 决定；审计默认折叠。
- 不允许关键操作被 `overflow-x: hidden` 静默裁切。

### 390 × 844

- 沿用移动顶栏与导航 Drawer。
- 默认显示队列；选择后进入单条详情视图，并提供 44px 明确返回。
- 详情连续展示证据、范围、AI 和决定，底部只保留一个安全主操作；其他动作进入次级区。
- 确认 Drawer 使用全宽单列表单，主按钮至少 44px。
- 页面级不得横向滚动；来源、缺失信息、期限和人工门禁不能因窄屏被删除。

## 6. 视觉语言与复用

继续复用 Ant Design：`Layout`、`Drawer`、`List`、`Typography`、`Tag`、`Badge`、`Button`、`Alert`、`Skeleton`、`Empty`、`Form`、`Descriptions`、`Collapse`、`Divider`、`Select`、`Input`。

复用今日工作台 token：

- 主色 `#315f8f`；
- 正文 `#17243a`；
- 次要文字 `#657083`；
- 边框 `#d8dee8`；
- 6px 圆角；
- 4/8/12/16/24 间距；
- 移动触控目标至少 44px。

红/橙只用于风险、错误和确定性阻断；蓝用于交互/系统信息；低饱和蓝紫用于 AI 建议；绿色只用于真实确认后的成功结果。使用 `Card variant="borderless"`，不得继续使用已弃用 `bordered` API。

## 8. 测试与浏览器验收

实施前新增 Playwright UI 契约测试，并用路由拦截提供明确的测试 Candidate/Analysis，不把 fixture 称为真实集成。覆盖：

1. 今日工作台主操作进入“待确认消息”；
2. 消息队列切换当前 Candidate；
3. 原始消息、上下文范围、附件缺口、AI 建议、推断和缺失信息可见；
4. 表单可人工修改 AI 建议值并安全取消；
5. 创建建议满足门禁时可进入确认 Drawer；非创建建议的正式创建被禁用；
6. 忽略、暂缓、关联/合并明确禁用且不发请求；
7. 空、加载、错误、无权限和详情失败状态；
8. 重新分析期间冻结确认；
9. 三个规定视口无页面级横向溢出，390 主操作和返回热区至少 44px；
10. 默认页与收件箱无 Ant Design 弃用警告。

真实浏览器截图保存在 `artifacts/ui-review/inbox/`，至少包含三个视口的改造前/最终主状态，以及必要的移动详情、确认表单和边界状态证据。最终报告写入 `docs/ui-review/inbox-02-visual-qa.md`。

完成门槛：0 blocker、0 high、无影响研判流程的 medium、无 Ant Design 弃用警告、无未经证明的在线/同步/成功状态，三个视口均可完成“队列 → 证据 → AI → 人工编辑 → 安全确认入口”的主要研判路径。
