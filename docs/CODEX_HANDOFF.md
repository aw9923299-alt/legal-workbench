## 4. 已知技术债

1. `App.tsx` 使用本地 state 切换页面，未采用 React Router，无法形成稳定 URL。
2. 多个页面直接导入 `src/data/mock.ts`，尚未统一经过应用服务或查询层。
3. `Task` 模型是原型最小字段集，尚未表达字段来源、人工确认状态、审计版本和实体关系。
4. AI 收件箱按钮主要是视觉交互，未形成可持久化的状态流。
5. 任务状态没有独立状态机，不能阻止不合法迁移或强制填写等待字段。
6. 缺少统一错误处理、通知、请求取消、重试和缓存策略。
7. 深色模式为基础 CSS 覆盖，尚未使用完整设计 Token。
8. 缺少单元、组件、端到端和可访问性测试。
9. `preview.html` 与 React 源码不是同一渲染链路，正式开发后可能出现视觉漂移。
10. 当前无后端仓库结构，需先决定 monorepo 还是前后端分仓。

## 5. 建议的下一迭代范围

建议第一个真实开发迭代只实现“本地可操作闭环”，暂不连接生产飞书：

```text
Mock 消息进入 AI 收件箱
→ 用户修改 AI 提取字段
→ 创建或关联任务
→ 任务进入待开始
→ 修改状态、等待对象和下一步行动
→ 记录变更时间线
→ 完成任务并生成结案草稿
```

这个范围可验证最关键的领域规则，并为后续飞书接入建立稳定的内部接口。

## 6. 建议技术方案

### 前端

- React + TypeScript + Ant Design；
- React Router 管理页面和任务 URL；
- TanStack Query 管理服务端状态；
- Zustand 或 React Context 管理少量本地 UI 状态；
- Zod 校验接口入参与 Agent 结构化输出；
- Vitest + Testing Library；
- Playwright 覆盖核心闭环。

### 后端/BFF

推荐先采用 TypeScript BFF：

- Node.js + NestJS/Fastify；
- PostgreSQL 保存任务、消息索引、审计和 Agent 运行记录；
- 对象存储保存授权范围内的派生文件；
- Redis/队列处理飞书增量同步、Agent 异步任务和提醒；
- 所有模型与飞书密钥仅保存在后端；
- OpenAPI 作为前后端契约。

这不是强制技术选型。Codex 如调整方案，应在 PR 中说明原因、迁移成本和对领域规则的影响。

## 7. 生产接入前置条件

在读取真实飞书消息前，必须先具备：

- 明确的 OAuth 与管理员授权流程；
- 可配置的会话白名单/黑名单；
- 私聊读取规则和显著告知；
- 原始权限快照和权限撤销处理；
- 消息撤回、编辑、删除和文件失效处理；
- 数据保留与删除机制；
- 审计日志；
- 敏感信息脱敏；
- 提示注入防护；
- 生产与测试数据隔离。

## 8. 完成标准

Codex 每次提交应在 PR 中列明：

- 用户场景；
- 改动范围；
- 领域规则；
- 数据和权限影响；
- 测试结果；
- 截图或录屏；
- 尚未完成的边界；
- 是否引入迁移或配置变化。
