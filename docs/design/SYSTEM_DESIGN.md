# 法务工作台总体设计

## 1. 文档目的

本文定义“法务工作台”的正式产品与系统设计，用于直接指导 Claude Code、Codex 或开发人员实施。设计基于当前 React + TypeScript + Ant Design 前端原型，并将其演进为运行在本地 Mac、通过 Docker Compose 部署、以飞书消息为入口、以 Codex 为唯一 AI 执行核心的法务工作系统。

本文不是页面概念稿。后续实现如果偏离本文的核心对象、审核门禁或 Agent 协议，应先形成新的架构决策记录。

## 2. 产品定位

法务工作台是法务专员的本地智能工作系统，目标不是自动替代法务判断，而是完成以下闭环：

```text
发现工作 → 理解工作 → 形成事项 → 拆解任务 → 执行专业作业
→ 形成审核包 → 法务审核 → 对外回复 → 跟踪进展
→ 结案复盘 → 沉淀经验
```

系统核心能力包括：

1. 接收经过授权的飞书机器人私聊、指定群聊、@消息、线程消息和附件；
2. 根据群聊和私聊的不同规则识别是否需要法务处理；
3. 判断消息应创建新事项、更新已有事项、补充材料还是仅供知悉；
4. 创建 `LegalMatter`，并拆解为可执行的 `WorkItem`；
5. 根据硬期限、风险、业务影响、发起人角色和现有工作负荷建议优先级；
6. 由确定性编排器调用 Codex 核心 Agent 和专业 Agent；
7. 通过本地知识库、历史审核样例和正式规则生成有依据的分析与回复；
8. 所有向他人发送的内容必须经过法务审核，并展示背景、依据、处理理由和风险；
9. 跟踪后续消息、等待状态、截止时间和重新开启；
10. 根据审核差异形成受控学习记录、日报、事项复盘和法务成长建议。

## 3. 非目标

第一阶段明确不做：

- 不读取法务个人账号的全部普通私聊；
- 不允许 Codex 或 Agent 绕过审核直接对外发送；
- 不允许 Agent 直接覆盖正式公司文件、合同原件或已确认事实；
- 不进行实时自动微调，也不让一次审核直接修改全局规则；
- 不以向量相似度代替资料版本、生效状态、适用主体和权限判断；
- 不在第一阶段同时实现全部专业 Agent；
- 不将 Docker 误认为能解决 Mac 关机、深度休眠或 Docker Desktop 停止的问题；
- 不把当前前端 Mock 页面描述为已经具备真实飞书、Codex、数据库或发送能力。

## 4. 总体架构

### 4.1 逻辑分层

```text
┌──────────────────────────────────────────────────────────────┐
│ Web Frontend                                                  │
│ 今日工作台 · 消息收件箱 · 事项中心 · 审核中心 · 知识库       │
│ Agent 中心 · 日报复盘 · 系统状态                              │
└──────────────────────────┬───────────────────────────────────┘
                           │ HTTP / SSE
┌──────────────────────────▼───────────────────────────────────┐
│ API / Application Service                                    │
│ Use Cases · Auth · Validation · Review Gate · Query Models    │
└───────────────┬──────────────────────────────┬────────────────┘
                │                              │
┌───────────────▼──────────────┐  ┌────────────▼────────────────┐
│ Legal Domain                 │  │ Manager Orchestrator         │
│ Matter · WorkItem · Review   │  │ Core Agent workflow          │
│ Deadline · Communication     │  │ retries · checkpoints        │
└───────────────┬──────────────┘  └────────────┬────────────────┘
                │                              │
┌───────────────▼──────────────────────────────▼────────────────┐
│ Workers / Codex Runtime / Knowledge Service                   │
│ Feishu events · file parsing · agent runs · indexing · report │
└───────────────┬───────────────────────────────────────────────┘
                │
┌───────────────▼───────────────────────────────────────────────┐
│ PostgreSQL · Redis · Qdrant · Local Object/File Storage       │
└──────────────────────────────────────────────────────────────┘
```

### 4.2 运行组件

| 组件 | 职责 |
|---|---|
| `web` | React 工作台，展示和提交人工操作，不直接访问飞书或 Codex |
| `api` | 业务用例、权限校验、审核门禁、查询聚合、OpenAPI |
| `feishu-connector` | 长连接、事件落库、附件下载、发送消息和回执 |
| `worker` | 事件消费、状态推进、重试、提醒、日报和索引任务 |
| `codex-runner` | 唯一 Codex 执行入口，会话隔离、工具权限、输出校验 |
| `file-indexer` | 本地目录监听、文件解析、版本与向量索引 |
| `postgres` | 领域数据、审计、元数据、全文索引和配置 |
| `redis` | 队列、锁、幂等、短期缓存和延时任务 |
| `qdrant` | 语义向量索引，不作为正式资料唯一来源 |
| `watchdog` | 服务健康、连接时延、队列堆积和 Codex 卡死监控 |

第一阶段允许将 `api`、`worker`、`feishu-connector` 和 `file-indexer` 实现在同一 TypeScript 后端代码库中，通过不同启动命令形成多个容器，避免过早微服务化。

## 5. 核心职责拆分

## 5.1 Manager Orchestrator

`Manager Orchestrator` 是确定性工作流服务，不是自由推理的万能 Agent。它负责：

- 根据领域状态选择下一步允许执行的步骤；
- 调用指定核心 Agent 或专业 Agent；
- 保存输入快照和输出；
- 执行 Schema 校验；
- 处理超时、重试、暂停和恢复；
- 在需要人工确认时创建工作台待办；
- 发现专业 Agent 冲突后暂停后续回复生成；
- 保证没有审核记录时发送服务不可执行。

它不负责生成法律结论，也不自行改变人工确认值。

## 5.2 核心 Agent

### 消息研判 Agent

输入消息和受控上下文，输出：

- 法务相关性；
- 消息作用；
- 行动性；
- 分类候选；
- 截止时间候选；
- 依据、置信度和不确定点。

不得直接创建正式事项。

### 事项归并 Agent

输出新消息与现有事项的关联候选，包括匹配分数和依据。支持：

- 新建事项；
- 更新事项；
- 补充材料；
- 变更期限；
- 记录决策；
- 重新开启；
- 一条消息拆分到多个事项。

### 任务规划 Agent

将事项拆成 `WorkItem`，并形成 `AgentExecutionPlan`。它负责建议，不负责绕过人工规则自动安排高风险工作。

### 优先级建议 Agent

只处理软判断：

- 发起人角色和业务关系；
- 是否阻塞上线、付款、开播或其他部门；
- 真实紧急程度；
- 重复催办；
- 当前工作负荷；
- 可快速解除阻塞的机会。

硬期限、逾期和法定节点由规则引擎计算。

### 结果汇总 Agent

汇总各专业 Agent 结果，区分：

- 已确认事实；
- 推断；
- 结论；
- 风险；
- 不确定点；
- Agent 之间的冲突。

冲突不能被静默融合。重大冲突必须形成审核项。

### 日报与工作复盘 Agent

基于系统查询产生的结构化事实底稿进行归纳，负责：

- 每日日报；
- 单项复盘；
- 周/月趋势；
- 阻塞和重复问题；
- 法务工作方法和专业成长建议。

不得凭长期会话记忆虚构完成情况。

## 5.3 专业 Agent

第一阶段注册但不必全部实现：

- 合同 Agent；
- 文案 Agent；
- 人力 Agent；
- 纠纷 Agent；
- 知产 Agent；
- 回复 Agent；
- 学习 Agent。

“检索 Agent”在实现上优先作为所有 Agent 可调用的受控知识工具；只有需要多步骤检索、冲突解析或研究型任务时，才作为独立 AgentRun。

## 5.4 确定性服务与 Agent 的边界

| 确定性服务负责 | Codex Agent 负责 |
|---|---|
| 飞书连接、事件存储、文件下载 | 消息语义理解 |
| 幂等、重试、锁、状态迁移 | 分类、关联和任务拆解建议 |
| 截止日期规则、逾期、SLA | 软优先级和业务影响判断 |
| 权限、审核门禁、发送 | 专业法律分析和回复草拟 |
| 文件版本、索引状态、备份 | 检索编排、冲突说明 |
| 日报事实底稿 | 日报归纳和工作复盘 |
| 审计和操作记录 | 审核差异分析和规则候选 |

## 6. 业务主流程

## 6.1 消息接入

```text
飞书事件到达
→ 校验事件签名和授权范围
→ 以 eventId/messageId 幂等落库
→ 保存原始载荷和最小可检索摘要
→ 下载授权附件并计算文件哈希
→ 创建上下文聚合任务
```

支持的首期来源：

- 发给法务机器人的私聊；
- 指定群聊中 @机器人的消息；
- 指定群聊全量消息（需管理员授权和白名单）；
- 法务手动转发给机器人的个人消息；
- 已有事项线程中的后续回复。

## 6.2 上下文聚合

系统生成不可变 `ContextSnapshot`，至少包含：

- 当前消息；
- 引用/回复链；
- 前后有限窗口消息；
- 参与人、群聊、部门信息；
- 附件及版本；
- 可能相关的历史事项摘要；
- 权限和生成时间。

Agent 只能基于该快照和明确授权的知识引用执行，不能默认读取整个飞书或整个本地目录。

## 6.3 消息研判和人工确认

```text
ContextSnapshot
→ 消息研判 Agent
→ MessageCandidate
```

候选结果包括：

- `create_matter`：建议创建新事项；
- `link_matter`：建议关联已有事项；
- `update_matter`：进度、决策或期限更新；
- `add_material`：仅补充材料；
- `information_only`：仅供知悉；
- `ignore`：与法务无关；
- `needs_confirmation`：信息不足。

任何低置信度、复杂多事项、重大风险、模糊期限或关联冲突必须进入工作台确认。

## 6.4 事项和任务形成

确认后创建或更新：

- `LegalMatter`：完整法务事项；
- `WorkItem`：事项下的具体行动；
- `Deadline`：一个事项可有多个不同性质的期限；
- `MatterSourceLink`：消息与事项的多对多关系。

不得以一个状态字段承载“处理中、等待材料、待审批、存在阻塞”等互不排斥的维度。

## 6.5 优先级确认

系统先计算硬规则，再调用优先级建议 Agent：

```text
硬期限/逾期/风险规则
+ AI 软建议
+ 当前工作负荷
→ PriorityProposal
```

以下情况要求法务确认优先级或完成时间：

- 建议为紧急或高；
- 无明确完成时间；
- 时间来自“尽快、晚点、今天看下”等模糊表述；
- 与现有高优先级工作冲突；
- 涉及诉讼、监管、平台处罚、重大金额或老板直接要求；
- 置信度低于配置阈值；
- 预计需要多个专业 Agent。

人工覆盖必须记录原建议、最终值和原因。

## 6.6 Agent 执行

```text
LegalMatter + WorkItem
→ AgentExecutionPlan
→ 人工确认（按策略）
→ AgentRun
→ DraftArtifact
```

执行计划支持顺序、并行、条件和冲突暂停。所有 Agent 运行必须绑定：

- 事项和任务版本；
- 输入快照；
- Agent/提示词版本；
- 允许的工具和目录；
- 预期输出 Schema；
- 超时和重试策略；
- 幂等键。

## 6.7 审核包和外发

所有向他人发送的内容统一形成 `ReviewPackage`，至少包括：

1. 原始需求；
2. 对话背景；
3. 已确认事实；
4. 未确认事实；
5. Agent 执行记录；
6. 专业结论和冲突；
7. 建议策略；
8. 为什么这样处理；
9. 风险和替代方案；
10. 引用依据；
11. 拟发送正文；
12. 接收人、会话和回复位置；
13. 置信度与限制。

法务可执行：

- 通过；
- 修改后通过；
- 驳回重写；
- 要求补充材料；
- 暂不发送；
- 转为内部记录。

发送服务必须验证审核版本哈希与待发送版本一致，获取飞书回执后生成 `Communication`。

## 6.8 后续跟踪和结案

发送后继续监听：

- 对方回复；
- 新附件；
- 决策变化；
- 截止时间变化；
- 任务完成或阻塞。

已关闭事项收到高关联新消息时，只能由系统建议重新开启，最终由法务确认或组织明确规则执行。

## 6.9 学习、日报和复盘

审核完成后，学习 Agent分析：

- 初稿与最终稿差异；
- 修改原因；
- 法律内容和表达内容的区别；
- 是否为个案；
- 是否可作为未来样例；
- 是否形成规则候选或知识缺口。

日报基于结构化记录生成事实底稿，再由复盘 Agent归纳。事实、判断和建议必须在 UI 中分区展示。

## 7. 页面设计落地

## 7.1 今日工作台

重点展示“现在应处理什么”：

- 硬期限和高风险；
- 待法务确认优先级/完成时间；
- 待审核回复和 Agent 结果；
- 等待材料、等待回复和阻塞；
- 管家建议排序及理由；
- 今日 Agent 运行和系统健康状态。

## 7.2 消息收件箱

每条候选展示：

- 原始消息和上下文；
- 群聊/私聊策略；
- 消息研判结果；
- 建议新建/关联/更新方式；
- 分类和期限候选；
- 依据、置信度和不确定点；
- 人工确认操作。

## 7.3 事项详情

主对象是 `LegalMatter`，而不是单一 Task。页面包含：

- 事项摘要和事实；
- WorkItem 列表；
- 多期限节点；
- 相关消息、文件和实体；
- AgentExecutionPlan 和 AgentRun；
- DraftArtifact；
- ReviewPackage；
- Communication；
- 审计和复盘。

## 7.4 审核中心

审核中心按风险和截止时间排序，支持：

- 专业作业审核；
- 外发消息审核；
- 优先级/完成时间确认；
- Agent 冲突处理；
- 学习规则候选确认。

## 7.5 知识库

知识库页面管理：

- 本地同步目录；
- 文件版本、生效状态和适用主体；
- 解析、全文索引和向量索引状态；
- 正式制度、模板、历史事项和审核样例的分域；
- 删除、失效和重建；
- Agent 检索引用记录。

## 7.6 Agent 中心

展示：

- AgentDefinition 和版本；
- 输入/输出 Schema；
- 工具和目录权限；
- 运行记录；
- 审核结果；
- 质量指标；
- 试运行/正式/暂停状态。

## 8. 异常和边界处理

## 8.1 事件重复

- 使用 `feishu_event_id` 和 `message_id` 唯一约束；
- 每个消费步骤拥有独立幂等键；
- 创建事项、执行 Agent 和发送消息不得因重试重复执行。

## 8.2 Mac 休眠或网络中断

- 连接自动重建；
- 保存最后成功游标和时间；
- 恢复后执行补偿同步；
- 未完成 Worker 作业从持久化队列恢复；
- 无法补拉的时间段必须在工作台显示告警。

## 8.3 Codex 失败

包括超时、非零退出、输出不符合 Schema、目录越权、工具调用异常：

- 记录失败类型；
- 按 AgentDefinition 重试；
- 超过次数进入死信；
- 不生成正式结果；
- 工作台提供人工重试、调整输入或终止。

## 8.4 文件版本冲突

- 每个附件和本地文件记录哈希、版本和来源；
- AgentRun 绑定明确版本；
- 新版本到达后，旧分析标记为“基于旧版本”；
- 未经重新执行或法务确认，不允许直接复用旧结论。

## 8.5 Agent 结论冲突

- 结果汇总 Agent标记冲突，不自动消解；
- 暂停回复 Agent或将冲突写入审核包；
- 法务选择采用结论并记录原因；
- 学习 Agent不得将冲突个案自动提炼为通用规则。

## 8.6 发送超时

- 每个 Communication 使用唯一幂等键；
- 请求超时时先查询飞书是否已经生成消息；
- 不确定时进入“发送结果待确认”，不得立即再次发送；
- 成功后保存飞书消息 ID 和版本哈希。

## 8.7 权限变化和删除

- 原始来源权限变化后，禁止继续向无权用户展示派生内容；
- 向量、全文索引和摘要必须同步失效；
- 处于 Legal Hold 的争议材料不得按普通删除策略清除；
- 删除操作生成不可变审计事件。

## 9. 安全设计

- 所有凭证放入后端环境变量或 macOS 钥匙串，不进入前端；
- 公司资料目录默认只读挂载给 `file-indexer`；
- Codex Runner 按 AgentRun 创建临时工作目录，只挂载授权文件；
- 文档内容视为不可信输入，禁止根据文档指令扩大权限；
- Agent 默认无发送、删除、权限变更和原文件覆盖能力；
- 日志不记录完整私聊、合同全文、个人敏感信息和访问令牌；
- 审核、发送、规则启用、知识失效和导出均进入审计日志。

## 10. 扩展原则

新增专业 Agent 时必须复用统一协议，不新增旁路：

```text
AgentDefinition → AgentExecutionPlan → AgentRun
→ DraftArtifact → ReviewPackage → ReviewRecord
```

新增数据源时必须先映射为 `SourceItem/SourceReference`，不得直接将供应商结构扩散到领域层。

新增自动化时应先判断：

- 是确定性工作流，还是需要 Codex 推理；
- 是否产生外发内容；
- 是否需要人工审核；
- 如何幂等、重试和回滚；
- 如何记录依据和版本。
