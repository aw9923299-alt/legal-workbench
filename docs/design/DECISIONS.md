# 关键架构决策

## ADR-001：Codex 是唯一 AI 执行核心

**状态：已确认**

系统不引入其他 AI 提供方，也不建设多模型供应商切换层。所有消息理解、任务规划、专业分析、回复生成、学习分析和复盘均通过本地 `Codex Runtime` 调用 Codex 完成。

保留 `Codex Runtime` 抽象的目的不是替换模型，而是统一控制：

- Agent 配置和提示词版本；
- 单次运行工作目录；
- 可访问文件和知识范围；
- 可调用工具；
- 超时、重试和输出校验；
- 会话隔离、日志与审计。

业务模块不得直接散落调用 Codex CLI。

## ADR-002：用户体验是统一管家，内部采用职责拆分

**状态：已确认**

前端对法务呈现一个“核心管家”，但后端由确定性 `Manager Orchestrator` 编排下列核心 Agent：

- 消息研判 Agent；
- 事项归并 Agent；
- 任务规划 Agent；
- 优先级建议 Agent；
- 结果汇总 Agent；
- 日报与工作复盘 Agent。

核心 Agent 只产生建议、分析和草稿，不直接改变正式状态或发送消息。

## ADR-003：消息、事项、行动任务和 Agent 产物分层

**状态：已确认**

核心链路固定为：

```text
FeishuMessage → MessageCandidate → LegalMatter → WorkItem
→ AgentExecutionPlan → AgentRun → DraftArtifact
→ ReviewPackage → ReviewRecord → Communication
```

不得将候选消息、完整法务事项、具体行动和外发回复压缩成单一 `Task` 对象。

## ADR-004：所有向他人发送的内容必须由法务审核

**状态：已确认**

范围包括业务回复、HR 沟通、老板汇报、外部律师或合作方回复、材料催办和对他人的自动提醒。只有本地界面提醒、内部日报草稿和个人工作建议不属于外发。

发送服务必须验证：

```text
ReviewRecord.decision ∈ {approved, approved_with_edits}
且审核版本与发送版本一致
```

否则拒绝发送。

## ADR-005：优先级采用硬规则、AI 建议和人工确认三层模型

**状态：已确认**

- 硬期限、逾期、法定节点和明确 SLA 由确定性规则计算；
- 业务影响、真实紧急程度、发起人角色和工作负荷由优先级建议 Agent 分析；
- 低置信度、高风险、模糊期限或与现有任务冲突时，由工作台要求法务确认。

最终优先级必须保存来源、理由和人工覆盖记录。

## ADR-006：知识检索采用混合检索，不以向量数据库替代正式规则

**状态：已确认**

Qdrant 用于语义召回，但检索必须同时使用：

- PostgreSQL 元数据过滤；
- 全文/关键词检索；
- 文件版本、生效状态、适用主体和保密等级；
- 审核通过样例和正式制度的分域索引。

过期、草稿、个案特例和未经批准内容不得默认进入正式依据。

## ADR-007：学习是受控记忆和规则审批，不是自动训练

**状态：已确认**

学习 Agent 分析原稿、最终稿和审核原因，输出：

- 审核样例；
- 表达偏好候选；
- 法律检查规则候选；
- 知识缺口；
- Agent 改进建议。

候选规则必须由法务确认、限定适用范围、通过回归评测后才可启用。

## ADR-008：Mac 使用 Docker Compose 部署，但主机休眠问题单独治理

**状态：已确认**

Docker 负责依赖隔离、健康检查和容器自动重启；`launchd` 负责开机拉起和主机级守护。Docker 无法在 Mac 关机或深度休眠期间继续接收消息，因此必须额外提供：

- 断线重连；
- 事件游标和补偿同步；
- 原始事件持久化；
- 未处理任务重放；
- 健康告警和备份。

## ADR-009：首个专业垂直闭环选择合同审核

**状态：已确认**

首个端到端实现范围：

```text
飞书合同请求 → 消息候选 → 事项/任务 → 公司资料检索
→ 合同 Agent → 结果汇总 → 回复 Agent → 审核包
→ 法务审核 → 飞书发送 → 学习记录 → 日报
```

其他专业 Agent 在统一协议和质量门槛稳定后接入。
